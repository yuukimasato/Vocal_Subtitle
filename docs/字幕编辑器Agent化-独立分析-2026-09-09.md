# 字幕编辑器 Agent 化：独立分析与修正建议

- 日期：2026-09-09
- 修订：v2 —— 追加**「作为独立开源组件发布、不得强绑定 Vocal_Subtitle」**这一硬约束，并据此反转 v1 中"复用上层 Python VAD"的建议
- 作者视角：第二意见（对《字幕编辑器Agent化方案-CLI与Harness-2026-09-09.md》的复核与修正）
- 状态：分析稿，未实施
- 方法：先实证再判断。本文所有"实测"标注均为本次会话在真实环境跑出的结果；未实测的推断均明确标注。

## 0. 结论

**方案方向正确，可以实施；但在"独立开源"约束下，它的复用策略需要反转，落地顺序需要调整。**

方案的核心判断——"需要做，但形态是三层薄接入而非无头编辑器"——我同意，并且**实测证明它比方案自己估计的还轻**：数据面 CLI 不需要新建工程，它已经存在了大约一半。

四点修正：

1. **`cli.mjs` 是薄包装，不是新工程。** 实测 `js/format/index.js`、`js/actions.js`、`js/audio/timing.js`、`js/state.js` 在 Node 24 中**零 shim 直接 import 成功**，无头全链路（解析 → 改时间 → 拆分 → 撤销重做 → 序列化）跑通。方案把 `cues`/`convert`/`check` 估为 2–3 天，实际主要成本在命令面设计与测试。

2. **独立开源把上层 VAD/CLI 从"复用对象"降级为"参考实现 + 可选 provider"。** v1 建议"Node CLI 子进程调用上层 Python VAD"——在组件化定位下最优，但在独立发布约束下**不可接受**：那会让开源组件的核心能力依赖一个未开源的私有项目。修正为：**组件必须自带一个能独立工作的确定性 VAD（Tier 3），上层 VAD 通过一个编辑器拥有并版本化的 JSON 契约以"可选 provider"身份接入（Tier 4）**。

3. **`peaks` 的定位被高估了。** `createPeakCollector` 是均值降采样（低通），刻意抹平起止瞬态——画波形对，定边界错。4kHz 的 0.25ms 是桶宽不是边界分辨率。但注意：**它同时是跨解码路径的归一化锚点**（浏览器采集兜底、ffmpeg、WAV 直读三条路都经它归一到 4kHz），这是"Agent 看到的数值与人在屏幕上看到的波形同源"的技术基础，应当显式文档化。

4. **方案完全没提独立发布的机械成本。** 实测编辑器**代码层面零耦合**（所有 import 都是工具目录内的相对路径，无任何父仓库引用），耦合只在**命名（4 处）与文档**上——独立发布的成本很低，但发布路径**尚未打通**：README 已指向 `github.com/yuukimasato/subtitle-editor/releases`，而 git remote 只有 `yuukimasato/Vocal_Subtitle`。

一句话概括：**组件自治，契约互操作**。编辑器自己拥有一切能独立工作的能力（字幕变换、峰值、边界候选、结构校验），上层只以"实现某个契约的可选外部提供者"身份接入，且这个契约写在编辑器仓库里。

## 1. 独立开源约束意味着什么

### 1.1 当前耦合盘点（实测）

| 类别 | 状态 | 位置 |
|---|---|---|
| 代码 import | ✅ **零跨目录** —— 全部相对路径（含 `../../vendor/*` 亦在工具目录内） | `js/**`、`build-standalone.mjs` |
| 运行时网络 | ✅ 无 CDN、无回传，vendor 全本地 | `vendor/NOTICE.md` |
| 许可 | ✅ MIT + vendor 声明齐备，商用友好 | `LICENSE`、`vendor/NOTICE.md` |
| 包名 | ❌ `vocal-subtitle-timing-editor` | `package.json:2,5` |
| 页面标题/品牌 | ❌ `字幕打轴工作台 · Vocal Subtitle` | `index.html:6,19,170` |
| README 标题 | ❌ `字幕打轴工作台（Vocal Subtitle Timing Editor）` | `README.md:1` |
| 发布路径 | ⚠️ README 指向独立仓库 releases，但 remote 仍是父仓库 | `README.md:15`、`git remote -v` |

结论：**代码已经是独立组件，只是还没被"当成"独立组件**。需要做的是命名清理、文档归属划分和发布机制，而不是解耦重构。

### 1.2 能力分层模型（本文的核心建议）

开源组件的最低可用性底线是：**Tier 0–3 在只有 Node 标准库时全部可用**。更重的能力一律"检测到即用、缺失即优雅降级"。

| Tier | 能力 | 依赖 | 缺失时行为 |
|---|---|---|---|
| 0 | 字幕读写 / 变换 / 结构校验 | 无（Node 标准库） | — |
| 1 | 波形数据：WAV 直读 → 4kHz 峰值流 | 无（纯 JS WAV 解析） | 非 WAV 报错退出（码 2），提示装 ffmpeg |
| 2 | 任意媒体解码 → 16kHz mono PCM → 4kHz | **可选** ffmpeg（探测到即用） | 退回 Tier 1 |
| 3 | **内置确定性 VAD**（能量 + 滞回） | 无 | 无音频输入时只做结构校验 |
| 4 | 高质量 VAD（Silero 等） | 用户自备 provider 命令 | 退回 Tier 3 |
| 5 | 真实页面驱动 / 截图复核 | Chrome + CDP | 不可用（不影响 0–4） |

三条分层原则：

- **Tier 3 必须存在且够用。** 否则开源组件脱离上层就只剩"改字幕文件"，作为"ASR 的功能补充"这一产品定位落空。Tier 3 的存在本身就是独立性的技术证明。
- **Tier 4 是集成，不是依赖。** 上层 VAD 只是"恰好实现了我们的契约的一个 provider"，换任何人实现都一样，缺失时组件照常工作。
- **所有解码路径经同一个 `createPeakCollector` 归一到 4kHz。** 这是测量一致性的锚点：Agent 从 CLI 拿到的数值，与人在浏览器波形上看到的是同一套数据。**这一点必须写进文档**——它是"数据优于视觉"能成立的前提。

### 1.3 内置 VAD（Tier 3）规格建议

不是要重造 Silero，而是要一个**确定性、可单测、精度够用**的边界候选器：

- **输入**：4kHz 单声道流（或 16kHz，内部同法处理）。
- **短时能量**：窗 20ms / 跳 10ms。跳长 10ms 与上层 `grid_resolution=0.01` 一致（该值也是打轴领域的常用取值，属收敛而非抄袭）。
- **噪声底**：帧能量取 20 分位。上层 `estimate_silence_rms(percentile=20)` 用同一思路。
- **判决**：阈值 = 噪声底 × 3；**滞回**：能量 > hi 进入语音、< hi/2 退出语音；`min_speech=150ms`、`min_silence=400ms`（与 ASR 生态惯例一致，也便于与上层参数对照）。
- **输出**：`[{start, end, confidence}]`，`confidence` 由超阈裕度映射；附 `engine: "energy-vad"` 字段。
- **精度声明**：干净素材 ±10–30ms；音乐/强噪声素材不保证。
- **定位声明**（写进 `--help` 与 JSON）：**这是打轴辅助的边界候选器，不是 ASR 分段器**。避免用户拿它去替代 Silero 并失望。

约 120 行，可完全单测（用 §7.1 的已知静音 fixture 断言误差 ≤ 50ms）。

### 1.4 外部 VAD provider 契约（Tier 4）

契约由**编辑器仓库拥有并版本化**，实现方（上层 Python、用户脚本、任何语言）只需满足它：

```
# 调用：cli.mjs vad media.mkv --provider "<cmd>"
# 请求（stdin，单行 JSON）
{"schema_version":"vad-provider-request-1","audio_path":"...","sample_rate":16000,
 "threshold":0.5,"min_speech_ms":150,"min_silence_ms":400}
# 响应（stdout，单行 JSON）
{"schema_version":"vad-provider-response-1","engine":"silero",
 "segments":[{"start":1.02,"end":3.00,"confidence":0.91}]}
# 退出码：0 成功；非 0 视为 provider 失败 → 自动退回内置 VAD 并在 JSON 中记录降级
```

上层项目只需在**它自己**的仓库里放一个约 20 行的适配脚本（把 `FFmpegSilenceVAD`/`SileroVAD` 的输出映射到上面的响应格式），即可接入。实测上层 VAD 的复用成本很低（`from vocal_subtitle.vad import FFmpegSilenceVAD` 0.25s；对素材 `detect()` 0.06s），写这个适配脚本没有障碍——**但它属于集成工作，不属于组件本身**。

## 2. 实证结果（方案文档没有的部分）

环境：Node v24.20.0、Chrome 152.0.7977.82、ffmpeg/ffprobe 可用、`node --test` 126 项全绿。

### 2.1 编辑器纯逻辑模块在 Node 中零 shim 可用（关键）

| 模块 | 无头 import | 说明 |
|---|---|---|
| `js/format/index.js` | ✅ | 导出 `detectFormat/parseSubtitle/serializeSubtitle/classifyClipboard/ensureDoc/makeNewCue/cueStyle/withCueStyle` |
| `js/actions.js` | ✅ | 内部对 `navigator`/`structuredClone` 已有环境判断 |
| `js/audio/timing.js` | ✅ | 头部注释明示"纯逻辑、无 DOM"，与实测一致 |
| `js/state.js` | ✅ | `createStore` 无 DOM 依赖 |

无头全链路实测：`parseSubtitle` → `loadSubtitle` → `updateCueTimes` → `nudge` → `splitCue` → `undo` → `redo` → `serializeSubtitle` 全部正确。

两个会踩的签名坑：`parseSubtitle(text, {filename, format})` 收选项对象；`serializeSubtitle(format, cues, doc)` 格式在前。

### 2.2 零依赖 CDP harness 技术可行（关键）

实测 Node 24 全局 `WebSocket`（无需 playwright）完成：`/json/version` → `/json/list` 取页面 target → `Runtime.evaluate` 往返 → `Page.captureScreenshot` 取回 PNG base64。方案 4.3 的技术路线成立。机器上同时有 `/usr/bin/google-chrome` 与 playwright 缓存的 chromium。

### 2.3 现有 fixture 无法用于 VAD/声学验收（硬伤）

| 素材 | 时长 | `silencedetect -35dB/0.4s` |
|---|---|---|
| `.fixture/test.wav` | 53.888s | 无任何静音输出 |
| `.smoke/mono.wav` | 30.000s | 无任何静音输出 |

`FFmpegSilenceVAD` 对 `test.wav` 返回单段 `0.000–53.888s`，印证"无静音边界"。

后果：方案 P2 的 `vad` 与 `check --media` **无法用现有素材验证**——它们依赖的正是静音结构。必须新增带**已知静音间隙**的 fixture（规格见 §7.1）。这是"验收标准不可执行"，不是"素材待补"。

## 3. 与方案文档的分歧

### 分歧 A（v2 反转）：`vad` 必须内置，外部只做 provider

v1 我建议"Node CLI 子进程调用上层 Python VAD"；在独立开源约束下**这条建议作废**。修正为 §1.3 + §1.4 的组合：

1. **Tier 3 内置 VAD 是默认路径**（零依赖，随时可用）；
2. **Tier 4 provider 是可选增强**（契约在编辑器仓库，实现在使用者仓库）；
3. 绝不 `import` 或硬编码任何上层模块路径。

方案 4.4 的 `vad <media>` 命令保留，但其实现应是"内置 VAD + 可选 `--provider`"，而不是"调用上层"。

### 分歧 B：`peaks` 降级为"可视化一致性"用途，不当测量主路径

`createPeakCollector`（`capture.js:34-84`）是**跨块均值降采样**，设计目标是"降采样后波形形状不失真"——为好看，不为定边界。方案 3.1 表格把"Agent 读峰值 JSON"列为测量主路径，会误导实现者去写包络拐点检测。

正确分工：

| 用途 | 正确工具 |
|---|---|
| 与人在屏幕上看到的波形一致（复核、截图、视觉模型输入） | `peaks`（4kHz） |
| 定位边界、生成候选段、判定"是否在波谷" | VAD（Tier 3/4）的语音/静音区间 |
| 与 ASR 文本对齐、最终裁决 | Agent（文本模型） |

方案"测量用数据、验证用视觉"的口号对，但把"数据"具体化成 peaks，这一步偏了。

### 分歧 C：视觉模型的正确定位是"替代人眼复核"，不是"初定位"

同意"视觉只用于验证"，补两条实现约束：

1. 视觉模型要回答**判断题**（"这条边界是否落在波谷内？"），不是**定位题**（"边界应该在哪？"）。判断题对 10ms/px 的像素误差不敏感，定位题敏感——这正是方案表格"±30–100ms"的来源。
2. `renderWaveform({t0,t1,pxPerSec})` 的标定元数据必须**烧进 PNG 本身**（角落水印 `t0=… pxPerSec=…`），否则 Agent 传给视觉模型时标定丢失，"读刻度"又退化成"猜"。

### 分歧 D：估时与验收不可执行（见 §2.3、§7.1）

### 分歧 E："进 CI"目前无 CI 可进

仓库内**无 CI 配置**（无 `.github/`、无 `.gitlab-ci.yml`）。`check` 的退出码价值是 **Agent 自闭环**与**人工闸门**，不是"进 CI"。建议措辞改为"退出码语义稳定，可被发布检查脚本或任何未来的 CI 消费"。

### 分歧 F：MCP 后置——同意结论，理由不同

方案说 MCP 是"薄包装、优先级最低"，同意优先级，但理由应是：**B（harness）已给 Agent 全部能力**，MCP 的增量仅是"工具描述自解释、省掉读文档成本"，是"同一能力的更贵封装"。在 `window.agent` 契约冻结前做 MCP，等于把未冻结的契约再包一层，返工翻倍。

## 4. 方案遗漏的三个风险

### 4.1 写路径：撤销步爆炸 + 草稿互相覆盖

**（1）撤销步爆炸。** `actions.commit()` 每次调用推一个快照（`actions.js:38-46`）。Agent 批量精修 200 行 = 200 个撤销步，人类终审时"Ctrl+Z 逐步回退"形同虚设。`commit()` 已支持 `coalesceKey`（自动提交拖拽就靠它合并），但**该参数没出现在方案的 agent API 里**。

建议：`window.agent` 暴露事务语义——`act(cmd, args, {coalesceKey})` 透传，或 `beginTransaction()/commitTransaction()` 让 Agent 声明一段工作共用同一 key。

**（2）草稿互相覆盖。** `draft.js` 按 `subtitleName || mediaName` 生成 localStorage key（`PREFIX='vstEditor.draft.'`），800ms 防抖写入。Agent 与人类**同源同 key**，Agent 工作 800ms 后人类未导出的草稿即被覆盖。

建议：agent 会话使用独立草稿命名空间（如 `?agent=1` 时 key 加后缀），或 agent 模式默认**不写草稿**、只在显式 `save()` 时写。这是"人机同屏监督"最容易出的数据事故，方案完全没提。

### 4.2 两套编辑器、两套波形栈、两条自动化路径

上层 WebUI 有自己的波形编辑器（`vocal_subtitle/webui/static/js/waveform.js`）和 Playwright e2e。再加 CDP harness 就是**第三条**。

建议：**harness 写成通用 CDP 客户端，不绑定 `window.agent`**——只提供 `open/attach/eval/shot/close` 原语，`window.agent` 只是被 `eval` 的目标表达式。这样同一份 harness 能驱动两边，也**更符合独立发布**（harness 属于通用工具，不含任何产品语义）。方案 4.3 的语义化子命令（`state`/`peaks`/`act`/`shot`）会把 harness 焊死在编辑器上。

### 4.3 `window.agent` 契约应冻结为 baseline 文件

仓库已有契约冻结惯例：`scripts/check_cli_contract.py`（`EXPECTED_COMMANDS`）、`scripts/check_api_contract.py` + `api_contract_baseline.json`。建议 `window.agent` 的**字段路径清单冻结成 baseline JSON**（如 `.smoke/agent-contract.baseline.json`），冒烟测试对真实页面求值后比对，字段增删即红。

## 5. 独立发布的结构性要求

### 5.1 命名去耦合（4 处，机械改动）

| 位置 | 现状 | 建议 |
|---|---|---|
| `package.json:2` | `vocal-subtitle-timing-editor` | `subtitle-timing-editor`（中性名） |
| `package.json:5` | 描述含 "Vocal Subtitle" | 去掉产品名，改为"零构建、零依赖的本地字幕打轴编辑器与 Agent 工具链" |
| `index.html:6,19,170` | 标题/品牌含 Vocal Subtitle | 中性品牌；页脚可保留"可与任意 ASR 流水线配合" |
| `README.md:1` | 标题含产品名 | 中性标题；新增一节「与 ASR 流水线集成」，把 Vocal_Subtitle 列为**消费者之一**而非归属 |

保留一处对 Vocal_Subtitle 的**正向引用**是合理的（"被用于…"），这不是绑定，是生态说明。

### 5.2 文档与契约的归属划分

这是独立发布后最容易出问题的地方——**契约必须由被依赖方拥有**：

| 内容 | 归属仓库 |
|---|---|
| Agent API 契约（`window.agent`）、CLI JSON schema、VAD provider 契约、编辑器不变量 | **编辑器仓库** |
| 集成文档、字段映射表、provider 适配脚本、"如何从流水线调用编辑器" | **上层仓库** |

本文目前**混合了两者**。建议按上表拆分：把 §1.4 的契约、§7 的验收留在编辑器仓库；把"与上层 VAD 的关系、字段映射、集成示例"移到上层 `docs/`。

### 5.3 防回归：把"不绑定"变成可执行断言

加一个单测（放在 `test/`，随 `node --test` 跑），扫描源码与页面中的禁止字符串：

- 禁止：`vocal_subtitle`、`Vocal_Subtitle`、`/home/hope`、绝对路径、任何 `../` 越出工具目录的 import；
- 允许：README/LICENSE/NOTICE 中作为"集成对象"的说明性提及（用白名单文件列表控制）。

这样"独立开源"从口号变成 CI 式断言——即使目前没有 CI，`node --test` 就是它的执行入口。

### 5.4 发布机制（尚未打通，需决策）

现状：README 指向 `github.com/yuukimasato/subtitle-editor/releases`，但 `git remote` 只有 `Vocal_Subtitle`，开发位置在父仓库 `tools/subtitle-editor`，另有 `subtitle-editor-standalone` 分支。

三种方案，按推荐排序：

1. **独立仓库 + 目录级同步脚本**（推荐）：新建 `subtitle-editor` 仓库，父仓库保留 `tools/subtitle-editor` 作为开发位，用脚本（`git subtree split` 或 rsync + 提交）单向同步。开发体验不变，发布产物干净。
2. **直接迁出**：编辑器完全移出父仓库，父仓库通过 release 产物或 submodule 引用。最干净，但开发链路要改。
3. **维持现状，只发布单文件 HTML**：不改仓库结构，仅把 `subtitle-editor-standalone.html` 发到独立仓库的 Releases。成本最低，但源码不独立，"开源组件"的叙事不完整。

无论选哪种，**§5.1 的命名清理都应先做**，否则同步出去的仓库自带父项目名。

## 6. 修正后的落地顺序

方案是 P0 AGENTS.md → P1 契约+harness → P2 CLI → P3 MCP。我建议插入"第 0 步"，并把 P1/P2 对调。

| 顺序 | 内容 | 理由 |
|---|---|---|
| **第 0 步（新增）** | 定 `check` 的语义边界 + 命名去耦合 + 防回归断言 | 先定"什么归编辑器、什么归 provider"，避免把外部语义固化进 CLI；命名清理越早做，同步出去的仓库越干净 |
| 第 1 步 | AGENTS.md（方案 P0） | 同意。追加：能力分层表（§1.2）、"禁止 import 上层"禁令、Tier 降级行为说明 |
| **第 2 步（方案里是 P2）** | Node CLI 数据面 `cues`/`convert`/`check`（结构性） | 实测几乎免费（§2.1），零外部依赖，立刻可单测。先落地它，Agent 立刻有确定性工具，不必等 harness |
| 第 3 步（方案里是 P1） | `window.agent` 契约 + 通用 CDP harness | 技术可行已验证（§2.2）。**前置**：§4.1 的 coalesce 与草稿隔离，否则人机同屏会出数据事故 |
| 第 4 步 | Tier 1–3：WAV 直读 + ffmpeg 解码 + 内置 VAD；Tier 4 provider 契约 | 依赖 §7.1 的新 fixture；provider 契约先定文档再定实现 |
| 第 5 步 | MCP 包装 | 同意方案：最后做 |

**为什么 P1/P2 对调**：harness 的价值依赖"人机同屏"，而人机同屏的前提是草稿隔离与事务语义就位。CLI 数据面不依赖任何这些，是纯增量、零风险、可立即验收的部分。先做确定的，把有语义风险的放后面想清楚。

## 7. 验收标准修正（可执行版）

### 7.1 新增 fixture 规格（替代方案 P2 对 `.fixture/` 的依赖）

- 16kHz 单声道 PCM WAV，总长约 20s；
- 静音段 ≥ 0.5s（高于 `min_silence=400ms`，确保可检出）；
- 建议结构：`[静音 0.0–1.0][音 1.0–3.0][静音 3.0–4.0][音 4.0–6.5][静音 6.5–8.0]…`，**每段静音的起止以常量写在测试里**；
- 断言：内置 VAD 输出的语音段起止与常量表误差 ≤ 50ms；`check --media` 能把人为移入静音区的边界标记为问题。

### 7.2 逐阶段可执行验收

| 阶段 | 验收（可执行） |
|---|---|
| 第 0 步 | 一页语义边界决定（结构检查归编辑器、声学判定可委托 provider）+ 命名清理完成 + 防回归单测通过 |
| 第 1 步 | 新会话 Agent 不读源码即可：起服务、跑测试、用 `?media=&subs=` 打开 fixture、复述能力分层与降级行为 |
| 第 2 步 | 每个子命令 JSON 输出 + `--format text`；`check` 退出码 0/2/3 有单测；`cues` 与 `actions.js` 行为一致性有单测 |
| 第 3 步 | baseline JSON 冻结 `window.agent` 字段；真实页面冒烟通过；**专项**：Agent 连续 50 次写操作后撤销栈深度可控（验证 coalesce）；Agent 会话不污染人类草稿 key |
| 第 4 步 | 内置 VAD 在 §7.1 fixture 上误差 ≤ 50ms；无 ffmpeg 时 WAV 直读可用、非 WAV 报错码 2；provider 返回非法 JSON 时自动降级且 JSON 中记录降级原因 |
| 第 5 步 | 与方案同 |

**可选的一致性验证**（不计入核心验收）：把上层 VAD 包装成 provider 后，与内置 VAD 在同一素材上对比段落差异，用于评估 provider 是否值得默认推荐。

### 8.2 与上层的可选映射表（引用，不依赖）

下列是上层 Vocal_Subtitle 的取值，**只作为集成文档里的对照**，不得成为编辑器代码的常量来源：

| 语义 | 上层取值 | 位置 |
|---|---|---|
| 硬静音阈值 | `DEFAULT_HARD_SILENCE_SECONDS = 0.4` | `acoustic/skeleton.py:12` |
| 吸附上限 | `max_snap_distance = 0.5`（配置）/ `0.25`（代码默认） | `config/loader.py:505`、`acoustic/validator.py:42` |
| 吸附余量 | `snap_start_margin=0.03`、`snap_end_margin=0.01` | `acoustic/validator.py:43-44` |
| 高置信跳过阈值 | `confidence_threshold = 0.6` | `acoustic/validator.py:47` |
| 融合网格/投票 | `grid_resolution=0.01`、`min_consensus=2/3` | `vad/boundary_fusion.py:25-34` |
| 合并 padding | `padding=0.10`、`min=0.05`、`max=0.20` | `merging/merge_strategy.py:48-51` |
| 间隙/长度 | `min_silence_gap=0.4`、`max_segment_length=20.0`、`min_fragment_duration=0.15` | `config/models.py:162-173` |
| 声学报告字段 | `snapped_starts`/`snapped_ends`/`rms_overrides`/`skipped_high_confidence`/`events_flagged`/`boundary_diagnostics` | `acoustic/validator.py:196-202` |

**重要：不要把上表的报告字段名抄进编辑器的 `check` 输出。** 理由：上层字段描述的是**"吸附算法做了什么"**（snapped_*、rms_overrides），而编辑器的 `check` 要描述的是**"字幕与音频的偏差是什么"**（重叠、间隙、过短、边界落在静音区）。语义不同，硬套会让 Agent 误解。编辑器应定义自己的、面向打轴问题的词汇（如 `overlaps` / `gaps` / `tooShort` / `boundaryInSilence` / `startAfterSpeech`），在集成文档里给出映射表。

另注意一处真实冲突：编辑器 `MIN_LEN = 0.05`（50ms）与上层 `min_fragment_duration = 0.15`（150ms）不是同一个量。编辑器 `check` 只对前者负责；后者的判定属于 provider/流水线侧。

## 9. 一句话总结

方案文档的架构判断（薄接入、不重写编辑器、数据优于视觉）是对的，可以照做；但在独立开源约束下，**复用策略必须反转**——上层 VAD 从"复用对象"变成"可选 provider"，组件必须自带 Tier 3 内置 VAD 才能独立成立。同时方案低估了已有资产（Node 可直接 import 编辑器逻辑）、高估了 peaks 的作用、漏了写路径的撤销/草稿风险、把验收标准建在了一份不适用的 fixture 上，也没提命名去耦合与发布机制。按本文 §6 的顺序与 §7 的验收清单实施，P0–P2 的实际工作量比方案估的一周更短，返工风险显著更低，且独立发布与流水线集成两条路互不阻塞。
