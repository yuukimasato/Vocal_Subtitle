# Vocal Subtitle 离线字幕全链路整体落实计划

日期：2026-08-02  
依据：[离线字幕全链路方案](离线字幕全链路方案-2026-08-02.md)、[当前运行时验收报告](superpowers/reports/2026-08-02-offline-full-chain-runtime-validation.md)、当前代码与配置审计。  
适用范围：离线批量字幕生产链、CLI、Web GUI、质量数据和反馈学习闭环。流式模式只保持兼容，不纳入本计划的质量优化范围。

## 1. 计划定位

本计划采用“框架先行、质量持续演进”的实施方式。

当前系统已经具备多条识别、物理校验、复核、反馈和导出能力，但这些能力的统一入口、运行状态、数据治理和持续学习机制尚未全部形成可运营闭环。第一目标不是围绕当前测试音频反复调参，也不是以一次性的固定黄金集分数决定项目是否可用；第一目标是让每一次真实离线任务都可以稳定执行、完整追溯、可人工修订、可安全反馈，并能将高价值修订逐步沉淀为可复用的质量资产。

后续质量提升应基于真实授权场景和用户反馈持续进行。固定评测数据仍然必要，但它只承担回归保护和版本比较职责，不能替代真实用户需求，也不能成为唯一的代码优化目标。

## 2. 总体目标与非目标

### 2.1 总体目标

1. 建立一条默认可运行、可降级、可追溯的离线生产主链：输入音频到 SRT/VTT/ASS 输出的每个关键结果均可定位其来源和处理版本。
2. 收敛所有会改变最终字幕的路径：文本候选、决策、物理投影、后处理和导出必须有明确的责任边界，避免绕过统一出口。
3. 建立面向真实使用的反馈闭环：人工修订能够安全归档、分析、审核、以影子方式验证，并在满足条件后形成场景化配置或优化样本。
4. 建立分层质量数据体系：工程诊断集、参考回归集、经审核的反馈样本集彼此隔离、版本化管理。
5. 建立可操作的发布治理：生产可用性以稳定性、可恢复性、无数据损坏、结果可解释和人工可接受为准；高精度质量指标用于持续优化和版本比较，不作为当前唯一的发布阻断条件。

### 2.2 非目标

- 不为提高某一固定测试集分数而做针对性规则、硬编码或阈值放宽。
- 不把项目已有 `test/` 音频、开发者临时样本或合成冒烟素材定义为黄金集标注基准。
- 不在主链责任、数据来源和回滚机制未稳定前，将所有可选引擎、自动学习参数或 LLM 能力同时设为默认。
- 不以“模型已下载”“组件可导入”作为引擎质量准入或发布依据。
- 不在本计划中变更模型许可、处理未经授权的数据，或将原始用户音频公开到仓库。

## 3. 当前基线与关键判断

### 3.1 已具备的基础能力

| 能力域 | 已有基础 | 本计划中的定位 |
|---|---|---|
| 主生产链 | 人声分离、宏观切块、VAD、ASR、时间映射、导出 | 收敛为唯一可解释的默认路径 |
| 物理证据 | `PhysicalTimeline`、词级分配、覆盖审计、字幕分箱 | 作为时间边界与覆盖审计的权威来源 |
| 多引擎复核 | global evidence、Context Re-ASR、Qwen、可选对齐/SED | 先做可观测候选，不直接扩大默认输出影响 |
| 决策与投影 | `EvidenceDecision`、`DecisionEventProjector`、coordinator | 作为最终文本选择和事件投影的唯一契约 |
| 后处理 | 说话人处理、语义合并、声学校验、最终化 | 只能在物理和决策约束内组织展示 |
| 反馈学习 | 字幕对齐、差异分析、参数学习、健康度、shadow/profile | 从“可写入”收敛为“可审核、可消费、可回滚” |
| 测试与报告 | pytest、质量脚本、运行报告、Web/CLI 冒烟 | 拆分为工程验证、参考回归和真实反馈评估 |

### 3.2 当前约束

- 当前 P0 架构收敛已形成主要的决策/投影骨架，但真实语音的召回和文本匹配仍有提升空间。
- `test/quality_manifest.yaml` 及其音频可用于发现回归、验证脚本和复现问题，但其来源、覆盖面、标注审核和代表性不足以作为正式黄金集基准。
- 用户反馈与真实授权音频尚未形成版本化样本池、审核流程、数据脱敏规范和统计报表，因此不能直接驱动默认生产参数。
- 多引擎、噪声画像和反馈 profile 的消费边界仍需在统一生产路径稳定后逐步启用。

## 4. 目标运行框架

### 4.1 生产数据流

```text
任务创建
  -> 输入校验、音频指纹和配置快照
  -> 人声分离 / 预处理 / 宏观切块
  -> 物理证据与时间线
  -> 分段主 ASR 候选
  -> 全局证据、风险识别和按需复核
  -> EvidenceDecision
  -> DecisionEventProjector + 覆盖审计
  -> 说话人、字幕组织和声学校验
  -> 导出、运行报告和可编辑结果
  -> 用户修订（可选）
  -> 反馈归档、对齐、差异分析、审核
  -> 场景 profile / 反馈回归样本 / 影子评估
```

### 4.2 四条必须闭合的链路

| 链路 | 目标 | 最小闭环证据 |
|---|---|---|
| 生产链 | 任何输入能得到可解释输出或明确失败 | task ID、配置版本、引擎状态、结果/失败原因、导出文件 |
| 决策链 | 所有最终字幕都可回溯到候选和物理范围 | candidate ID、decision ID、projection trace、退化状态 |
| 反馈链 | 人工修订可被安全分析但不会立即污染默认 | 原始版本、修订版本、对齐质量、diff、审核结论、回滚记录 |
| 质量链 | 数据、指标、问题和改进可持续累积 | 数据集版本、样本来源、评估版本、场景切片、趋势报告 |

### 4.3 核心不变量

1. 分段主候选是默认生产基线；global ASR 和副引擎首先是证据来源，只有满足明确准入契约时才可影响对应风险窗口。
2. `EvidenceDecision` 是文本选择出口；`DecisionEventProjector` 是权威模式的事件投影出口。任何兼容或降级路径也必须留下明确追踪。
3. `PhysicalTimeline` 决定字幕不能跨越的物理边界。语义、角色和格式化可组织文本，但不能伪造语音范围或越过硬静音。
4. 自动学习默认只产生建议和影子结果；未经审核和回归验证，不能自动改写全局默认配置。
5. 原始素材、人工标注、用户修订、诊断结果和发布产物必须分别标明来源、授权状态、保留期限和版本。

## 5. 数据与评测治理

### 5.1 数据集分层

| 层级 | 名称 | 来源与用途 | 是否作为发布硬门禁 | 管理原则 |
|---|---|---|---|---|
| D0 | 工程诊断集 | 单一功能、合成片段、临时复现音频、现有测试素材 | 否 | 允许随功能增加；用于单元/组件/端到端回归 |
| D1 | 参考回归集 | 已审核、可复现、场景覆盖明确的内部授权样本 | 阶段性 | 只用于版本趋势和明显退化发现，不追求穷尽真实需求 |
| D2 | 候选反馈集 | 用户同意留存的原始任务和人工修订结果 | 否 | 自动入库后先脱敏、去重、质量检查，不直接训练或调参 |
| D3 | 反馈回归集 | 从 D2 中完成授权、匿名化、标注审核和分层抽样的样本 | 是，逐步启用 | 版本冻结后只增量演进，保留来源与审核记录 |
| D4 | 场景挑战集 | 长音频、多人重叠、噪声、中英混合等高风险真实样本 | 否 | 用于识别短板和设计新能力，不以单次失败阻断一般发布 |

### 5.2 测试素材的明确边界

- 当前 `test/` 目录音频、`quality_manifest.yaml`、合成 TTS、重复短语与非语音样本统一归入 D0，必要时可被挑选为 D1 的候选，但在补齐授权、标注审查、场景标签和版本记录前不得称为黄金集。
- D0 的失败应定位工程回归、接口错误或可复现缺陷；它不等价于“真实用户不可接受”。
- D1/D3 的失败应按场景和严重度分析。普通版本发布不因个别高难样本失败而无限期阻塞，除非涉及数据损坏、字幕严重误导、崩溃或大范围退化。
- 禁止基于单一 D0/D1 样本添加面向特定文本、文件名、时间点或录音特征的代码分支。

### 5.3 反馈样本生命周期

```text
用户修订
  -> 同意留存与用途确认
  -> 加密/受控存储，生成不可逆样本 ID
  -> 自动质量检查和重复检测
  -> 自动字幕与人工字幕对齐
  -> 差异归因与置信度计算
  -> 人工审核：接受 / 拒绝 / 待补充
  -> 进入候选反馈集
  -> 分层抽样、匿名化和二次标注
  -> 冻结为反馈回归集版本
  -> 用于影子评估、场景 profile 验证和趋势分析
```

每个反馈样本至少记录：样本 ID、数据来源类型、授权状态、语言、场景、时长、音频条件、说话人数、原始配置版本、引擎/模型版本、自动字幕版本、人工修订版本、对齐质量、审核人、审核结果、保留期限和脱敏状态。原始路径、用户身份、密钥和不必要的文本内容不得出现在公开报告或提交记录中。

### 5.4 标注与审核规则

1. 人工修订不自动等价于真值。修订可能包含风格偏好、删减、重写或遗漏，必须区分“内容更正”“时间调整”“格式偏好”“角色标注”和“结构性改写”。
2. 进入 D3 前至少完成一次独立审核；争议样本标记为 `disputed`，不用于自动参数决策。
3. 对齐覆盖不足、音频/字幕不匹配、语言不确定或结构性重排的样本只保留作诊断，不进入自动学习样本。
4. 每个反馈集版本记录纳入/剔除原因、样本分布和已知偏差，确保后续可以复现评测范围。

## 6. 分阶段落实计划

阶段按依赖顺序推进。每个阶段结束必须形成可运行产物、验证记录和明确的下一阶段输入；不要求等全部质量目标达到后才进入下一阶段。

### Phase A：基线冻结与工作治理

目标：建立可协调的实施边界，避免并行改动互相掩盖问题。

实施项：

1. 建立版本状态表：记录当前默认配置、模型版本、依赖锁定、支持平台、已知限制和生产档位。
2. 建立架构决策记录（ADR）目录，优先固化“统一决策出口”“物理边界优先”“反馈影子消费”“数据集分层”四项决策。
3. 为每个现有方案/设计/计划建立索引，标记状态为已实施、部分实施、待实施、已废弃或仅供参考，避免历史文档互相矛盾。
4. 固定任务命名、运行 ID、配置快照、模型标识、报告位置和变更日志格式。
5. 将当前测试素材清单登记为 D0，删除其“黄金集”语义，保留其作为工程回归与问题复现输入的价值。

交付物：架构状态表、ADR 索引、数据资产登记表、当前基线报告模板、文档状态索引。

完成标准：团队可以回答“某次输出由什么版本产生、用了什么配置、问题应查哪个报告”；不需要等待质量分数提升。

### Phase B：生产主链与可观测性收敛

目标：任何离线任务都有统一的运行状态、诊断和降级行为。

实施项：

1. 固化默认 `quality-first` 生产档位：分段主候选、global evidence、保守复核和已知可用的物理/声学校验；将实验选项与默认选项明确分离。
2. 统一任务生命周期：排队、预检、运行、降级完成、失败、取消、导出完成；CLI 与 Web 使用同一状态语义。
3. 每次运行持久化最小可观测包：输入指纹、配置快照、依赖/模型 availability、路径选择、阶段耗时、警告、异常类别、输出统计、可定位制品链接。
4. 收敛 global、segmented、骨架、Chunk、恢复和兼容路径，确保最终事件都具有 candidate/decision/projection 或降级 trace。
5. 统一错误分类与用户提示：模型缺失、依赖缺失、资源不足、音频格式不支持、引擎超时、可恢复降级、不可恢复失败分别处理。
6. 为长音频、模型不可用和 Web 任务恢复建立资源与超时边界，避免单任务影响其他任务。

交付物：统一运行报告 schema、任务状态机、引擎可用性快照、默认/实验配置清单、降级行为矩阵。

完成标准：任一支持格式的任务要么导出字幕，要么返回可行动的失败原因；不出现无来源的最终字幕事件；可选引擎不可用时主链仍能完成基础任务。

### Phase C：物理、决策与展示契约完成

目标：将时间、文本选择和显示组织拆成稳定契约，给后续引擎与学习能力提供安全接入点。

实施项：

1. 完成候选证据统一模型：每个候选保留来源、时间坐标、词级时间可用性、置信度、语言、窗口、物理范围、诊断和版本。
2. 完成 `EvidenceDecision` 的动作与原因记录；`keep/replace/split/drop/unresolved` 均有输入证据与结果追踪。
3. 完成 `DecisionEventProjector` 的权威投影、覆盖审计和降级投影规则，禁止未经记录的 raw bypass。
4. 统一 offset、宏块、骨架、窗口和全局时间的坐标转换测试；同一偏移只应用一次。
5. 保持词级证据到最终句级 cue 的可追溯性，确保字幕组织不跨硬静音、明确物理 bin 或不可兼容的说话人变化。
6. 把后处理能力限制在显示层职责内：角色、标点、语义合并、格式化不能破坏物理边界、决策文本和时间追踪。

交付物：证据/决策/投影契约说明、诊断样例、回退策略、覆盖审计报告、路径回归测试。

完成标准：对任意字幕 cue 可定位到其候选、决策理由和物理范围；遇到证据不足时选择保守保留或 `unresolved`，而非静默删除或伪造时间。

### Phase D：配置、引擎与模型能力治理

目标：让可选引擎成为可管理能力，而不是分散开关。

实施项：

1. 定义引擎生命周期：`unavailable`、`model_missing`、`ready_shadow`、`ready_review`、`ready_default`，并将状态写入运行报告。
2. 将“要复核哪些窗口”（cover policy）与“使用哪些引擎”（engine policy）拆分，保留旧配置的兼容映射。
3. 为每个引擎提供统一预检、模型路径、运行资源、超时、语言适配、输出时间能力和降级策略声明。
4. 建立实验注册表：引擎、模型、量化方式、设备、配置组合、适用语言、预期收益、已知风险、启用范围、撤回条件。
5. global ASR、Qwen、FunASR、ForcedAligner、SED 和语义复核先从 shadow 进入；影响默认输出必须经过样本回放、人工检查和可撤回验证。
6. 将引擎选择、模型下载与运行时可用性分开显示，避免“选择了某引擎”被误解为“实际参与了本次输出”。

交付物：引擎注册表、能力状态面板、配置迁移表、模型预检报告、实验结果模板。

完成标准：用户和维护者可从一次运行报告判断每个引擎是未安装、不可用、仅影子运行、实际复核还是默认生效；任一引擎失败不会无提示地改变生产质量或阻塞基础输出。

### Phase E：反馈学习闭环与场景化配置

目标：使反馈学习从“写入功能”成为受控的产品能力，并逐步产生有用的场景适配。

实施项：

1. 在 CLI/Web 中明确反馈入口：用户上传修订字幕时关联原任务、展示用途说明，并允许选择“不保留音频/仅本地分析/允许匿名化改进”。
2. 完成自动字幕与人工修订的对齐质量门控、差异分类、结构性修订识别和低可信反馈降权。
3. 将学习结果分为三类：展示偏好（标点、说话人标签）、结构偏好（合并/拆分）、声学/识别问题（漏词、错词、边界）。三类不得混用同一参数更新策略。
4. 每次学习先生成“建议 profile 版本”和预期影响，不直接覆盖用户当前默认；保存输入、建议、前后差异、健康度和可回滚版本。
5. 以 shadow mode 在已授权样本和后续同类任务上比较建议 profile 与基线 profile；只在无明显退化、样本量足够、适用场景明确时允许用户或管理员启用。
6. 生成反馈回归集候选：从高价值、已审核、可匿名化的反馈中按语言、场景、难度和错误类型抽样，形成 D3 的增量版本。
7. 对 profile 设置作用域与过期机制：用户级、场景级、设备级或全局级；当模型、VAD 或主链版本改变时自动重新验证或回退。

交付物：反馈同意与数据策略、反馈记录 schema、审核队列、profile 版本与回滚机制、影子比较报告、反馈集版本清单。

完成标准：一次用户修订可以被可靠关联、解释和撤回；它不会立即改变其他用户的输出；经审核的反馈可被稳定地转化为场景优化依据或回归样本。

### Phase F：质量运营与持续优化

目标：在框架稳定后，以真实需求驱动质量提升，而非追逐单一固定分数。

实施项：

1. 建立质量问题分类：可用性、完整性、文本准确性、时间准确性、说话人、格式可读性、性能、成本和可解释性。
2. 建立场景切片：语言、单/多人、背景噪声、音乐、远场、快语速、长音频、专业词汇、设备和资源档位。
3. 每个版本对 D0/D1/D3/D4 输出趋势而非单一总分：通过率、失败类型分布、人工严重度、耗时、资源消耗、回退率和用户修订率。
4. 使用“问题优先级 = 影响范围 × 用户严重度 × 可复现性 × 修复置信度”安排优化工作；高频真实问题优先于固定样本上的边际提升。
5. 每次质量改动都进行对照运行：基线配置、候选配置、必要时 shadow，且报告说明受益场景、退化场景和不确定性。
6. 累积足够 D3 样本后，再逐步把场景阈值、回归线和发布建议固化；阈值应是历史数据和业务风险的产物，不是先验目标。
7. 定期归档低价值或过时样本，避免反馈集被某类用户、某个语言或某个模型版本过度主导。

交付物：月度质量报告、问题看板、数据集版本、实验对照报告、场景 profile 发布说明、版本回顾记录。

完成标准：优化决策可说明其来源于哪些真实问题和哪些数据切片；用户修订率、严重问题率、稳定性和性能呈可解释趋势；没有人为扩大单一回归集的权重。

### Phase G：发布、支持与维护治理

目标：把技术能力转化为可支持、可回退的发布流程。

实施项：

1. 明确三类发布状态：`development`（开发验证）、`production-usable`（正常需求可用）、`quality-improving`（持续优化中）。只有在证据充分时再添加更严格的认证标签。
2. `production-usable` 的最低标准为：安装和启动可靠、基础任务可完成、关键失败可解释、输出不损坏、可选能力失败可降级、人工编辑和反馈入口可用、重大回归可回退。
3. 建立发布前检查单：依赖锁定、模型可用性、迁移兼容、核心自动化测试、D0 回归、少量 D1 回放、CLI/Web 冒烟、文档/启动器一致性。
4. 建立发布后观测：崩溃/失败率、任务耗时、降级率、导出失败、用户撤销/编辑率、反馈提交率和高严重度问题。
5. 建立问题升级与回滚机制：配置回滚优先于代码回滚；模型/引擎变更要支持独立禁用；数据集错误必须可撤销其评估结论。
6. 维护用户可见的限制说明：适用音频、离线资源要求、多人重叠/高噪声等已知挑战、输出需要人工校对的边界。

交付物：发布检查单、版本说明模板、支持与回滚手册、运行监控指标说明、已知限制清单。

完成标准：系统即使仍存在复杂场景的质量缺口，也能作为正常离线字幕工具稳定使用、被支持和持续改进。

## 7. 验证策略

### 7.1 三层验证

| 验证层 | 关注点 | 输入 | 触发时机 | 通过准则 |
|---|---|---|---|---|
| 工程验证 | 接口、契约、回归、错误处理 | D0、mock、临时复现样本 | 每次提交/变更 | 无关键回归，异常可预测 |
| 运行验证 | CLI/Web、真实管道、资源和降级 | D0/D1 的少量可复现样本 | 每个里程碑 | 任务可完成，报告完整，输出可打开 |
| 质量运营验证 | 用户可接受度和真实场景趋势 | D1/D3/D4 分层样本 | 版本/月度 | 无大范围退化，关键问题趋势改善 |

### 7.2 必做检查

1. 单元与组件测试：配置解析、坐标换算、候选契约、决策动作、投影、反馈对齐、profile 回滚。
2. 集成测试：默认生产路径、可选引擎缺失、global 失败、复核失败、projector 失败、长音频、缓存恢复、CLI/Web 导出。
3. 人工抽检：每个发布版本抽取不同语言和场景的结果，检查内容是否明显丢失、时间是否明显错位、是否跨静音、是否可阅读。
4. 反馈抽检：审核对齐错误、结构性修订、异常 profile 建议和误归因案例。
5. 性能与资源检查：典型机器的运行时长、峰值内存/显存、超时和降级比例。

### 7.3 不以单一阈值阻断的规则

- D0/D1 的指标用于警报、趋势与问题排序；除非发现严重数据损坏或大范围回归，不因一次未达固定分数无限期阻断普通版本。
- D3 形成前，任何“黄金集”结论必须注明其只是参考回归结论，不能泛化为整体真实质量。
- 新能力优先采用 shadow 和场景对照。没有足够反馈样本时，结论应标记为“证据不足”，而非通过修改阈值获得通过。

## 8. 里程碑、依赖与优先级

| 里程碑 | 前置依赖 | 主交付 | 可进入下一阶段的条件 |
|---|---|---|---|
| M1 框架基线 | 无 | Phase A 状态表、ADR、数据分层 | 文档、版本、数据命名统一 |
| M2 可运营生产链 | M1 | Phase B 任务与报告闭环 | 默认任务可运行/可降级/可追溯 |
| M3 统一契约 | M2 | Phase C 证据、决策、投影契约 | 无 raw bypass，时间/来源可追溯 |
| M4 能力治理 | M2、M3 | Phase D 引擎生命周期与实验注册 | 可选引擎状态透明、可撤回 |
| M5 反馈闭环 | M1、M2、M3 | Phase E 反馈审核和 profile shadow | 单次反馈不污染默认，能回滚 |
| M6 持续质量运营 | M4、M5 | Phase F 数据版本与趋势报告 | 可按真实场景安排优化 |
| M7 稳定发布治理 | M2 至 M6 | Phase G 发布/支持/回滚流程 | 可作为正常需求的生产工具维护 |

优先级规则：M1-M3 为必须先完成的框架；M4-M5 可在 M3 稳定后并行推进；M6-M7 是持续工作，不应被理解为“达到某一个固定分数才开始”。

## 9. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 过度拟合测试素材 | 真实用户质量不升反降 | D0/D1/D3/D4 分层；禁止样本特定规则；报告按场景切片 |
| 用户反馈质量参差 | 错误 profile 或错误基准 | 对齐门控、审核、置信度、结构性修订隔离、可回滚 |
| 原始音频隐私/授权不清 | 合规与信任风险 | 显式同意、最小存储、受控访问、匿名化、保留期限、删除机制 |
| 多引擎复杂度失控 | 输出不可解释、资源浪费 | 生命周期、实验注册表、shadow 准入、独立开关和超时降级 |
| 历史文档与代码漂移 | 维护成本和错误实施 | 状态索引、ADR、每阶段实现报告、过期文档标记 |
| 质量改动引起隐藏退化 | 新场景受损 | 分层对照、影子运行、版本回退、保留失败样本 |
| 模型/依赖升级变化 | 运行失败或结果漂移 | 依赖锁定、模型指纹、可用性预检、升级独立实验 |

## 10. 每个工作包的执行模板

后续具体实施任务均按以下模板立项，避免“大方案直接改代码”。

1. 问题陈述：来自用户反馈、运行报告或工程回归的可复现现象。
2. 影响范围：受影响场景、用户、生产档位、是否涉及数据/隐私风险。
3. 假设与证据：明确已知事实、不确定点和要收集的日志/样本。
4. 方案边界：涉及的模块、数据、配置和明确不改动的部分。
5. 验证设计：D0/D1/D3/D4 中选取何种输入、人工抽检方式和预期不退化项。
6. 回滚方案：配置、模型、代码和数据结论分别如何撤回。
7. 交付物：代码、测试、报告、文档、迁移说明、发布说明。
8. 完成判定：以可运行、可追溯、可回退和场景化结果为主，不以一个脱离上下文的总分为唯一条件。

## 11. 建议的首批实施顺序

1. 建立 Phase A 的文档状态索引、ADR 与数据集登记，先统一语言和边界。
2. 完成 Phase B 的任务/报告/引擎可用性统一输出，确保默认生产链可运营。
3. 完成 Phase C 的候选、决策、投影追踪收敛，消除影响后续扩展的路径歧义。
4. 并行准备 Phase E 的反馈数据规范、同意流程和审核 schema；此时不启用自动参数消费。
5. 完成 Phase D 的引擎生命周期和实验注册，逐项将已存在的可选能力纳入影子治理。
6. 从真实授权反馈中积累 D2，定期审核形成首个小规模 D3；在样本分布足够后才定义场景化回归线。
7. 以 Phase F 的真实问题趋势安排识别、时间轴、说话人和展示质量优化；每轮改动都有独立的对照与回滚结论。
8. 达到 Phase G 的生产可用标准后保持正常发布，质量提升作为持续版本演进，而非无限期阻断。

## 12. 完成定义

本整体计划完成不等于“字幕质量已经在所有场景达到最高精度”。其完成定义是：

- 系统的生产、决策、反馈和质量四条链路均有稳定边界和可执行流程；
- 测试素材不再被误用为黄金集基准，真实反馈可合法、安全、可审核地沉淀为数据资产；
- 质量提升具备持续输入、分层数据、场景化评估、影子验证和回滚能力；
- 项目可以面向正常离线字幕需求稳定交付，同时明确复杂场景的限制并持续优化；
- 后续每个优化任务都能从本计划的框架中找到数据来源、接入位置、验证方式和停止条件。
