## 0. 结论(TL;DR)

1. **统一模块 + 四个入口**:学习数据收集是一个闭环,四个场景只是不同的进入路径,用场景标签区分——`inline-review`(V1 工作台内修正)、`external-correction`(V2 外部工具修正上传)、`existing-subtitle`(V3 存量字幕学习)、`from-scratch-timing`(V4 从零打轴)。
2. **现状基本是"纯收集"**:四类学习产物(参数 overrides / few-shot 缓存 / 音频指纹 / D2 样本)**没有任何一项在管线运行时被消费**;参数 overrides 的合并函数已写好但全仓库零调用(§1 事实核查)。
3. **最大真实缺口是 V2**(外部工具修正上传,无音频上传 + 任务绑定);V1 基本已实现;V3/V4 语义已被 `run_pipeline_first` 覆盖,差异步化。
4. **性价比最高的单项改动是 task_id 引用学习**:带 task_id 时基线直接取任务已存的 `result_json` events——消灭"永远重跑"、修复 `skip_separation` 基线不一致、补全 D2 样本元数据。
5. **数据集导出打通外部训练闭环**:只导 accepted 样本,`dataset-v1` 格式(文本对+音频引用),git-ready 目录手动推送;模型回流一律走现有 engine/provider 契约。
6. **"立即使用"是一扇建好但默认关着的门**:参数 overrides 接线落地,`feedback.apply_overrides_on_run` 默认 `false`(D38);V2 检索影子先行(D37)。

## 3. 四个场景的最终形态

| 场景 | 入口 | 基线来源 | 学习通路 | 现状 → 增量 |

## 5. 边界收口与声明假设

- **未点学习但导出的本地 `.journal.jsonl`**:开关关=惰性本地文件(用户可手动推送或 CLI 离线 ingest,通道 B);开关开=导出即上送,不存在此状态。
- **自动学习 × 异步任务**:导出触发的是异步学习任务提交(V3/V4),不阻塞导出;V2 场景自动学习不适用(上传本身即显式动作)。
- **V4 journal 无管线出处**:从零打轴没有 manifest,provenance 为空是预期行为,学习走 feedback 通道不受影响。
- **声明假设(可否决)**:V4 阶段 MCP 服务形态 = 8613 HTTP API 的薄包装(stdio MCP 入口),不新写业务逻辑;数据门禁打开前不做设计深化。
- **遗留观察(实施时复核,非本次决策)**:`dry_run` 预览目前也会入库 D2 样本(F5),接入场景标签时一并复核是否应只在确认学习时入库。
